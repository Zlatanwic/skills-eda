## 这场答辩的故事主线（先记住这一条线）

整份 PPT 其实在讲一个完整的故事，五句话就能串起来：

1. **问题**：skills 正在变成 agent 的复用单位，但我们把它当普通 prompt 用，从不分析它"要求什么能力、依赖什么环境"。
2. **视角**：SkVM 论文给了我一个角度——把 skill 看成"自然语言程序"，把 model/harness 看成"执行目标"，于是"能不能跑"就变成"需求 vs 能力"的匹配问题。
3. **数据**：我把这个视角变成可计算的东西——从 skill 文本派生 **SCR（需求）**，导入 SkVM 的 **TCP（目标能力）**，两者相减得到 **gap（迁移风险）**。
4. **发现**：用 dashboard 一层层看下去——skills 高度流程化、文档生成是最大瓶颈、风险既来自模型也来自 harness、六成 skills 依赖外部环境，最后用 PCA/聚类看出 skill 家族和异常点。
5. **边界**：这是一个 **SkVM-inspired 的 EDA dashboard**，不是 SkVM 编译器/运行时的复现——我做的是分析、可视化和解释。

**每次翻页时，心里都回到这条线**：现在讲的是"问题 / 视角 / 数据 / 发现 / 边界"中的哪一段。下面每页结尾我都给了一句【串场】，专门负责把上一页和下一页缝起来，让评委始终知道你走到哪了。

总时长建议 **14–16 分钟**。第 14–16 页（Advanced EDA）和第 12–13 页内容最多，时间紧时优先压这几页。讲的时候始终记住一句话：**不是在展示一堆图，而是在证明 skill 这种文本对象可以被数据化、被解释、被比较。**

## 第 4 页 · 为什么 skills 值得分析

**【画面】** 标题"为什么 skills 值得分析"；右侧三个问题：直接塞进上下文 / 缺少能力需求分析 / 缺少运行环境风险分析。

**【讲稿】**
随着 agent 系统的发展，skill 正在变成一种重要的**复用单位**——它可以告诉 agent 怎么做代码审查、怎么用 GitHub、怎么生成文档、怎么分析数据。

但现在的用法有三个问题。**第一，直接塞进上下文**：系统并不真正理解这个 skill 对模型能力、对运行环境有什么要求，塞进去就指望它能跑。**第二，缺少能力需求分析**：一个 skill 里其实藏着多步骤流程、工具调用、代码片段、验证步骤——它更像一段**自然语言写的程序**，但我们从没把这些"要求"提取出来。**第三，缺少运行环境风险分析**：很多 skill 要跑 shell、读写文件、装 npm 包、调 API key，环境不匹配它就会失败，但没人量化过这个风险。

所以我的出发点是：**如果不分析 skill 的结构和能力需求，就根本没法判断它在不同模型、不同框架上是否可靠。** 这正是一个值得做探索性分析的对象。

**【串场】** 那"把 skill 当程序分析"这个视角从哪来？这就是 SkVM 论文给我的启发。

## 第 5 页 · Inspired by SkVM

**【画面】** Inspired by SkVM；采用：对 skills 的量化系统分析视角 / primitive requirement 思路 / TCP profile vs SCR 的比较思路。

**【讲稿】**
SkVM 论文最关键的一句启发是：**skills 可以被看作自然语言程序，而不同的 model 和 harness 是不同的执行目标。** 既然是执行目标，能力就有强弱；既然 skill 有需求，就可以拿"需求"和"目标能力"去比对，看匹不匹配。

我从 SkVM 借了三样东西：**第一，量化系统分析的视角**——不靠主观感觉，而是把 skill 拆成可统计的特征和能力需求。**第二，primitive requirement 的思路**——把"这个 skill 要求什么底层能力"表达成一组带等级的 primitive。**第三，也是最核心的，TCP profile 和 SCR 的比较思路**——SkVM 用 TCP（Target Capability Profile）描述一个目标能提供什么能力，我则从 skill 文本派生 SCR（Skill Capability Requirement），两者一比，就得到迁移风险。

**这里必须强调边界**：SkillScope 是 **SkVM-inspired 的 EDA dashboard**，我**没有**实现 SkVM 的 compiler 和 runtime。我关注的是分析、可视化和解释——这条边界我在最后一页还会专门交代。

## 第 9 页 · 数据处理流程 + SCR/TCP/Gap 指标

**【画面】** 上半：处理流程；下半：SCR/TCP 定义、Level L0–L3、`gap = max(0, required_level − provided_level)`。

**【讲稿】**
整个 pipeline 是这样一条链：
`Skill Markdown → 特征提取 → Taxonomy 分类 → SCR 抽取 →（可选 LLM 辅助）→ SCR/TCP Gap → Advanced EDA → Dashboard`。

简单说：先把三路 `SKILL.md` 统一成 JSON；做**特征提取**（长度、词数、section 数、code block 数、step count、是否有 branching/loop/verification、工具与依赖证据）；做 **taxonomy 分类**（tool-reference / procedural / generative / mixed）；然后**抽取 SCR**——先用规则方法给出 primitive、level 和 evidence，再对 20 条 SkVM benchmark skills 用 LLM 做了 `rule+llm` 辅助标注，提升关键样本质量。技术栈是 Python 处理 + Vue 3 / Vite / TypeScript / ECharts 做前端，dashboard 读静态 JSON。

下半页是**核心指标**，这是理解后面所有图的钥匙：
- **SCR**：skill 的能力需求；**TCP**：某个 model/harness 提供的能力；
- 能力分 **L0–L3**：L0 没有、L1 基础、L2 标准多步骤、L3 复杂组合（含分支、验证、多工具协作）；
- **gap = max(0, 需求等级 − 提供等级)**。举例：skill 需要 `tool.github` 到 L3，但目标只提供近似能力 L1，gap 就是 2。把一个 skill 所有 primitive 的 gap 加起来，就是它对某个目标的 **portability risk**。

**【串场】** 指标讲清楚了，下面进入第三部分——这是整个项目的核心：用 dashboard 把这些指标一层层可视化出来。

## 第 11 页 · Skills：语料画像与样本下钻

**【画面】** Skills 页面：分类（Taxonomy）/ 语言统计（Code Languages）/ Risk-rank 表格 + 右侧 detail；"点击跳转 dashboard"。

**【逐图分析】**

- **Source mix / 分类（Taxonomy）**：分类环形图把 skill 分成 tool-reference、procedural、generative、mixed。它回答 skill 的**角色结构**——是偏工具说明、偏流程执行还是偏内容生成。tool-reference 和 procedural 占比高，正好支撑我的核心叙事：**skills 更像操作规程和程序，而不是知识卡片**。
- **语言统计（Code Languages）**：统计 fenced code block 里的语言（bash、python、typescript…）。它说明 skills **不是纯自然语言**——大量嵌入了可执行代码，这也解释了为什么后面 environment risk 和 harness risk 那么重要。
- **Risk-ranked skills + detail panel**：左边按 overall risk 排序，**点一个 skill，右边显示它的 taxonomy、长度、step、code block、risk radar、top primitives 和 evidence**。

**【讲稿】**
Skills 页负责两件事：**语料画像**和**样本下钻**。前两个图给出整体画像——来源构成、类型构成、代码语言构成。

但我想特别强调右下角这个 **Risk-ranked 表格加 detail panel** 的设计。这是 EDA 里很关键的一点：**图表发现异常之后，必须能回到原始样本去解释异常。** 我点开一个高风险 skill，右侧立刻展示它为什么高风险——它的 primitive evidence、风险雷达、依赖证据都在。这让我的风险分数**不是黑箱**，每一分都能追溯到 skill 文本里的具体证据。

**【举例 · 点开排第一的 `cli`，演示一次追溯】**（这段是 detail panel 的现场用法，可结合实时 dashboard 讲）
我现场就拿**排在第一的** skill 来追溯一次。表格按 overall risk 降序排，此刻榜首是一个来自 public GitHub 的 skill，名字就叫 `cli`，risk pill 是 **39**——它教 agent 怎么用 TypeScript/Go 从零搭一个命令行工具。一行数字看不出名堂，但**点开它，右侧 detail panel 就把这 39 分一层层拆开**：

1. **先看基本画像，知道它为什么"重"**：类型是 tool-reference，可篇幅有 **16,728 字符、33 个 section、12 个 step、21 段代码块**——它本质是一篇完整的工程教程，不是一张知识卡。这是它进入高风险区的第一个线索。
2. **再看风险雷达（Risk profile），定位风险来自哪**：`environment_mismatch` 直接顶到 **100**，而 `model_mismatch` 和 `harness_mismatch` 都只有 **19**。一眼就能下判断：它高风险**不是因为模型不够聪明，而是因为它对运行环境要求太多**。
3. **再看 Top primitives，知道它要求什么能力**：它一口气需要 **20 个 primitive，而且几乎全部压在 L3**——`data.parse`、`gen.code.typescript`、`gen.code.shell`、`tool.package_manager`、`runtime.env_bind`、`tool.github`…… 是个典型的"全能型"skill，难怪 environment 风险被顶满。
4. **最后看 Evidence，让每一项都落回原文**：`tool.package_manager` 这条来自文本里真实出现的 `npm install`、`package.json`；`runtime.env_bind` 来自 `environment variable`、`setup`；依赖信号里还能直接看到 `token`、`secret`。所以那个顶满的 environment 风险**不是我拍脑袋给的**——它由 skill 文本里这 8 条依赖证据撑起来。

这就完成了一次完整的追溯：**risk pill 39 → 风险雷达告诉我"是环境问题" → primitive 告诉我"它要 20 项 L3 能力" → evidence 把它钉回 `npm install`、`token` 这些原文词**。顺带一提，evidence 也是我**自查规则误报**的工具——比如这条 skill 被打上了 `spreadsheet.process`，点开 evidence 一看只是正文里出现了 `excel` 一词，这种近似就能当场识别出来，而不是被风险分数蒙混过去。

补一句它在 Risks 页的下文：detail panel 里的 bottleneck 显示它聚合 gap 最高的是 `reason.plan`（25）和 `doc.generate / tool.github / tool.web.*`（各 18）；但它的**最佳目标是 `openclaw / deepseek-v4-pro`，total_gap 只有 1**。也就是说——**连这个看起来最吓人的 skill，换到对的 model/harness 组合上也几乎能跑**，这正好预告了第 13 页"迁移风险是组合属性"的结论。

这里也能顺带说明代码实现：前端不是把图写死在 PPT 里，而是 Vue 读取 `summary.json`、`skills_index.json` 和 `portability.json`，再用 ECharts 渲染；全局 filter 改变后，图表和样本表会一起联动。所以它既是展示页面，也是一个可以继续探索的 EDA 工具。如果老师感兴趣，我可以现场点开 dashboard 看任意一个样本。

**【串场】** 画像告诉我们"skills 长什么样"，但还没回答"它们到底要求什么能力"。这就是 Primitives 模块。

## 第 12 页 · Primitives：能力需求结构

**【画面】** Primitive Level Heatmap / Primitives demand ranking / Workflow complexity map。

**【逐图分析】**

- **Primitive Level Heatmap**（核心图）：横轴 L1/L2/L3，纵轴 primitive，颜色越深表示该 primitive 在该等级上越多。它回答的不只是"需要什么能力"，而是"**需要到什么复杂度**"——一个 primitive 大量压在 L3，说明它往往涉及复杂组合、验证或多工具协作。
- **Primitives demand ranking**：最常见能力需求排名。当前最突出的是 `follow.constraints`、`follow.procedure`、`follow.verify` 这类**流程型** primitive——说明 skill 的核心不是"知识"，而是"**按规则、按步骤、带验证地行动**"。
- **Workflow complexity map**：横轴 step count、纵轴 primitive diversity，每个点一个 skill。**右上角**的点步骤多、能力也杂，对模型和 harness 要求最高，往往就是迁移风险或重写优先对象。

**【讲稿】**
Primitives 页专门拆解 skill 的能力需求。最值得看的是 **Level Heatmap**：它把能力需求从"频率"进一步细分到"复杂度"。配合右边的 demand ranking，我们能得出一个很重要的判断——**当前 skills 高度流程化**：最常见的不是花哨的代码生成，而是约束遵守、步骤执行和结果验证。`follow.constraints` 出现在 **1,680 个 skills、占 96.6%**；能力需求排名里，`follow.procedure` 有 **1,622** 次，`follow.verify` 有 **1,502** 次。另一个独立统计是 verification-heavy workflows：**1,448/1,739，也就是 83.3%** 的 skills 文本里出现了 test/check/verify 这类验证信号。

而 complexity map 让我们看到复杂度的分布——少量右上角的 skill 又长又杂，它们是后面风险分析和重写排序里最该盯的对象。

**【串场】** 既然知道了 skills 需要什么能力，下一个自然的问题是：这些能力在不同目标上**够不够**？不够会怎样？这就是 Risks 模块。

## 第 13 页 · Risks：迁移风险与环境风险

**【画面】** Target compatibility / Dependency·Environment Risk（核心是 Model×Harness 思路）。

**【逐图分析】**

- **Model × Harness Portability（思路核心）/ Target compatibility**：把所有 target profile 按平均 gap 排序。结论很直接——当前**最兼容的目标是 `deepseek-v4-pro / openclaw`，平均 gap 仅 0.344**；不同组合差异明显。这证明一件事：**portability 不是只看模型强不强，也不是只看 harness，而是 model/harness 这一对的组合属性。**
- **Risk Components（拆解）**：把风险拆成 model mismatch、harness mismatch、environment mismatch。当前 **model mismatch ≈ 0.136、harness mismatch ≈ 0.143**——非常接近，但 **harness 略高，主导失配轴是 harness**。这回答了我第 4 个研究问题：**fragility 不能只怪模型，运行框架和工具支持同样关键。**
- **Dependency / Environment Risk**：统计 system cli、version control、web/browser、runtime、credentials、package managers 等类别。

**【讲稿】**
Risks 页回答"这些能力为什么会在某些目标上失败"。两个结论我想重点讲。

第一，**迁移风险是组合属性**：同一批 skills，换个 model/harness 组合，平均 gap 可以差很多，所以"选目标"本身就是一个值得优化的决策。

第二，**环境依赖是被严重低估的风险**。Dependency Risk 图显示，**1,105 个 skills、占 63.5%** 都提到了依赖、凭据、包或环境配置。也就是说——**哪怕模型本身足够强，只要目标环境缺了 CLI、GitHub、runtime 或 API key，skill 照样会失败。** 这正是为什么我坚持把 environment mismatch 作为一个独立的风险维度，而不是混进模型能力里。

**【串场】** 到这里，单变量和双变量的分析已经比较充分了。但 EDA 的精髓是从单变量走向**多变量结构**——共现、矩阵、降维、聚类。这是 Advanced EDA 三页要做的。

## 第 14 页 · Advanced EDA（一）：共现与桑基

**【画面】** Primitive 共现矩阵 / Taxonomy × Primitive 桑基图。

**【逐图分析】**

- **Primitive Co-occurrence Matrix**：行列都是 primitive，颜色表示两个 primitive 在同一个 skill 里共同出现的次数。它发现的是**能力组合模式**——比如 `follow.procedure` 和 `follow.verify` 频繁共现，说明"**执行步骤 + 验证结果**"是一个非常典型的 skill 模板；tool 类 primitive 常和 file/Git/环境绑定共现。结论：**skill 的能力需求不是单点，而是成组出现的结构。**
- **Taxonomy × Primitive Sankey**：左边是 taxonomy，右边是 primitive，流量粗细表示需求强度。它把**两套标签体系连起来**——tool-reference 主要流向 tool/file/package/GitHub，procedural 流向 follow.procedure/verify/constraints，generative 流向 doc.generate。这样 taxonomy 就不再是孤立标签，而是能**解释能力需求差异**的结构变量。

**【讲稿】**
前面我们一直在看单个变量的分布，Advanced EDA 开始看**变量之间的关系**。共现矩阵告诉我们哪些能力"总是一起出现"，桑基图告诉我们"哪类 skill 流向哪类能力"。这两个图共同说明：**skills 是由多种能力需求组合成的多变量结构，不能用单一标签去概括。**

**【串场】** 看完关系，再看分布和单样本画像。

## 第 15 页 · Advanced EDA（二）：矩阵与分布

**【画面】** Source × Language 热力图 / Skill × Primitive 矩阵 / 长度·步骤直方图。

**【逐图分析】**

- **Source × Language Heatmap**：行是来源、列是语言、颜色是 code block 数量。用来**比较不同来源的技术风格**——本机 skills 工具链更重时，bash/python 会更突出；public sample 作为初步外部对照。
- **Skill × Primitive Matrix**：纵轴是 **36 个 high-risk / primitive-dense skills**，横轴是 top primitives，颜色是 required level。代码里这 36 个样本按三项排序取出：overall risk、primitive 数量、step count。也就是说，它不是随机样本，而是故意把最值得检查的复杂样本放到一张矩阵里。这个图的价值是从"总体统计"回到"单个 skill 的能力画像"：例如某些行几乎在 `follow.constraints`、`tool.git`、`doc.generate`、`reason.plan` 上同时变深，就说明该 skill 对流程、工具和生成能力都有高要求。
- **长度 / 步骤直方图**：最基础但很重要的分布分析。两个分布都是**长尾**——少量特别长、步骤特别多的 skill，会对上下文长度、推理稳定性和迁移性造成压力，是异常样本的来源。

**【讲稿】**
这一页是经典 EDA 的"分布 + 矩阵"组合。我想特别说 **Skill × Primitive 矩阵的选样逻辑**：它不是为了代表全体样本，而是为了把最复杂、最值得人工检查的样本集中展示出来。也正因为这样，它更适合回答"哪些 skill 需要优先解释、重写或进一步验证"，而不是回答"整体分布是什么"。整体分布已经由前面的 demand ranking、level heatmap 和直方图承担了。

**【串场】** 关系看了、分布看了，最后一步是把所有特征压到一起，用降维和聚类看 skill 的"全局地图"。

## 第 16 页 · Advanced EDA（三）：PCA 与聚类

**【画面】** PCA / k-means 聚类散点图。

**【逐图分析】**

- **PCA / Clustering Map**：每个点一个 skill，坐标来自 PCA 投影，颜色来自 k-means 簇。我用**结构特征 + SCR primitive 特征**构造向量——文本长度、词数、section 数、code block 数、step 数、dependency 数、tool 数、有没有 branching/loop/verification，加上 top primitives 的 required level——先标准化，再 PCA 降到二维，最后 k-means 粗聚类。

**【讲稿】**
这是项目里机器学习方法的部分，也是 Advanced EDA 的收尾。需要强调：**PCA 和 k-means 在这里不是用来预测，而是用来探索结构。** 它帮我看到 skills 是否形成若干家族——比如工具密集型、文档生成型、代码生成型、流程控制型；也帮我找出**远离主簇的异常点**，那些往往是又复杂又高风险的 skill。

这一步正好完成了 EDA 的标准弧线：**从单变量分布，走到双变量关系，再走到多变量结构发现。** 到这里，我对这批 skills 的画像就比较完整了。

**【串场】** 分析做完了，最后我要诚实地交代：这个项目和 SkVM 到底是什么关系，边界在哪。

# 第四部分：总结与展望（第 17–18 页）

## 第 17 页 · 与 SkVM 的对齐和 gap

**【画面】** 三列：Implemented / Partial / Out of scope。

**【讲稿】**
这一页专门划清边界，避免把一个 EDA dashboard 误讲成 SkVM 的复现。

- **已实现（Implemented）**：skill collection、SCR extraction、TCP import、gap analysis、dashboard visualization——也就是"把 skill 当自然语言程序来分析"这条完整链路。
- **部分近似（Partial）**：primitive mapping（我的 primitive catalog 和 SkVM 不完全一致，只能映射到最接近的 SkVM primitive）、environment risk（我做的是**风险检测**而非自动生成 setup script）、concurrency signals（简化成复杂度信号，没有真生成 DAG）。
- **不在范围（Out of scope）**：AOT compilation、JIT code solidification、adaptive recompilation、runtime speedup evaluation。

所以准确定位是：**SkillScope = SkVM-inspired exploratory dashboard**。我借用了 SkVM 对 skills、primitive、TCP 的视角和它的 TCP 数据，但贡献在"分析、可视化、解释"，不在"编译、运行、加速"。

**【串场】** 在这个边界之内，我得到了哪些结论，又有哪些局限和后续方向？

## 第 18 页 · 结论、局限与未来工作

**【画面】** Findings 卡片 + 局限 + 未来工作。

**【讲稿】**

**主要结论**（直接对应研究问题）：
1. **Skills 高度流程化**——最常见能力是 `follow.constraints`（**1680 / 96.6%**），verification 类覆盖 83.3%；
2. **文档生成是最大瓶颈**——`doc.generate` 的聚合 gap 高达 **18,150**；
3. **最兼容目标是 `deepseek-v4-pro / openclaw`**（平均 gap **0.344**），portability 与 model/harness pair 强相关；
4. **环境依赖是普遍风险**——**1105/1739、63.5%** 的 skills 涉及依赖/凭据/包/环境；
5. **主导失配轴是 harness**（model 0.136 / harness 0.143）——fragility 不能只怪模型；
6. **多变量 EDA**（共现、桑基、矩阵、PCA/聚类）能发现 skill 家族和异常点。
   （另：LLM SCR 辅助标注 20 条，是独立统计 tile，不计入 8 条 findings 卡片。）

**局限**：SCR 主要是规则派生 + 20 条 LLM 辅助，**不是人工金标**；public sample 只有 95 条，只能做初步对比；primitive mapping 是近似；PCA/k-means 只用于探索、不用于预测；未实现 SkVM 的 runtime/compiler。

**未来工作**：扩大 public sample、做人工 SCR validation、引入更完整的 embedding/clustering、推进 task-level evaluation。

**收束语**：
总结一句话——**SkillScope 把原本隐藏在 skill 文本里的能力假设和运行风险，变成了可观察、可比较、可解释的分析结果。** 从课程角度，它完整覆盖了 EDA 的主要方法：多源数据整合、特征工程、分布分析、共现分析、热力图、桑基图、散点图、降维、聚类、交互式过滤和样本级下钻。我的汇报到这里，谢谢各位老师，请老师们提问。

## 备用问答（高频）

**Q：你是不是复现了 SkVM？**
A：不是。SkillScope 是 SkVM-inspired 的 EDA dashboard。我借用了它对 skills、primitive、TCP 的视角和 TCP 数据，但没有实现 compiler/runtime（见第 17 页）。

**Q：SCR 标签可靠吗？**
A：SCR 主要是规则派生，适合探索性分析，不是人工金标。我已对 20 条 SkVM benchmark skills 合并了 `rule+llm` 辅助标注，后续需要人工 validation sample 审核。每个 SCR 都有 evidence，可在 Skills 页 detail panel 追溯。

**Q：public 样本只有 95 条，够吗？**
A：不够代表完整公共生态，它的价值是**证明 pipeline 已能接入公开 GitHub 样本**，并提供初步外部对照。扩大样本是明确的未来工作。

**Q：为什么用 PCA 和 k-means，而不是做预测？**
A：本项目是探索性分析，不是预测任务。PCA 把多维结构/能力特征压到二维便于观察，k-means 帮助发现 skill 家族和异常区域，簇的含义需结合 detail panel 人工解释。

**Q：gap=2 这种值具体怎么算的？**
A：`gap = max(0, required_level − provided_level)`。比如某 skill 需要 `tool.github` 到 L3，目标只提供近似能力 L1，该 primitive 的 gap 就是 2；把一个 skill 所有 primitive 的 gap 聚合，就是它对该目标的迁移风险。

**Q：这个项目和这门课的 EDA 关系是什么？**
A：它完整覆盖了 EDA 与可视化的主要方法——多源整合、特征工程、分布/共现分析、热力图、桑基图、散点图、降维、聚类、交互式过滤和样本级 drill-down，并且做到了"从图表到结论"的叙事组织。
